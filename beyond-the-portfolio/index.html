STUDY C—01 / DOCUMENTATION

Generative studies

WHAT IT IS

A visual study built from simple shapes: rings, grids, panels, and small points of light. It is a piece of decorative motion, not a chart, and the shapes do not stand for measured data.

PURPOSE

The study tests how much depth a page can gain from a small set of geometry and lighting rules, without bright effects or large assets. The aim is a sense of space that supports the writing rather than competing with it.

HOW IT WORKS

On this site one Three.js renderer draws every scene on a single shared canvas. Each scene has its own group of shapes; when you navigate, the outgoing group fades while the incoming group appears. Ring rotation and camera position ease toward the pointer, so movement is subtle instead of abrupt. Rendering is capped, pauses after inactivity or when the tab is hidden, and stops entirely for reduced motion or smaller devices, which use a static gradient instead.

The wider portfolio has a separate Three.js space scene with a grid, orbit rings, and wave bars. Its scroll-linked timing is coordinated with GSAP ScrollTrigger and the Web Animations API.

TECHNOLOGIES

Three.js and WebGL for the geometry, JavaScript for the scene states, CSS transforms and opacity for the crossfade, plus GSAP ScrollTrigger and the Web Animations API in the portfolio's scroll motion. No second 3D library was added.

INTERACTION

You can move the pointer to gently shift the field, move between scenes, and observe a different arrangement in each one. There are no controls for changing values, and nothing on screen represents live measurements.

RELEVANCE

The same approach suits product pages, launch pages, and case studies that need a quiet spatial layer behind real content. Because the renderer is shared and gated by device and motion settings, it can be reused without loading a heavy animation stack into every section.

CURRENT STATUS

Implemented here: the shared-canvas scenes, pointer response, idle and hidden-page pause, and static fallbacks. Implemented separately in the portfolio: the space scene and scroll-linked motion. Proposed only: packaging these studies as a reusable component or binding them to real data.

STUDY C—02 / DOCUMENTATION

Interaction sketches

WHAT IT IS

Small interface studies about state and focus: details panels, press-to-choose controls, and a two-sided profile card in the main portfolio. Each one is a way to test an interaction pattern rather than a finished product feature.

PURPOSE

These sketches check whether an interaction that looks elaborate still has a plain keyboard path, a visible focus state, and an honest label. The aim is that motion never hides how a control actually works.

HOW IT WORKS

Details and documentation panels use the browser's native dialog element. Opening one places it in the top layer, keeps keyboard focus inside, dims and blurs the scene behind it, and supports Escape; the close handler returns focus to the button that opened it. On the deployed concept page, three tabs use aria-selected, arrow keys, Home, and End to switch panels, while finance range, stock filter, and PC metric buttons update sample text and bars in place and mark the chosen button with aria-pressed. The main portfolio's profile card swaps faces by changing a state attribute and mirroring it with aria-expanded, aria-hidden, and inert so only the visible face can be reached.

TECHNOLOGIES

HTML dialog elements, JavaScript event handlers, CSS transforms and opacity, and ARIA state attributes including aria-pressed, aria-expanded, aria-hidden, and inert. The portfolio's reveals also use the Web Animations API and GSAP ScrollTrigger.

INTERACTION

You can open and close detail panels, press Escape, move focus with Tab, switch concept tabs with arrow keys, and choose a sample range, stock filter, or PC metric on the deployed concept page. The profile scene is a static presentation with no flip control.

RELEVANCE

Useful for settings panels, onboarding, dashboards, and documentation overlays where a modal must remain keyboard-safe. The pressed-button pattern applies to any segmented control or filter that changes what is shown below it.

CURRENT STATUS

Implemented: the prototype's detail and documentation panels, the concept page's sample toggles, the production profile flip, and reduced-motion handling. Proposed: collecting these patterns into a shared component library.

STUDY C—03 / DOCUMENTATION

Local tools / notes

WHAT IT IS

A set of local-first utility ideas and the notes around them: a browser activity tracker, sample dashboards for finance and PC health, and documentation about keeping data on the device that produced it.

PURPOSE

The goal is to explore useful tools that need no account and no hosted service, and to show clearly which figures are illustrative samples and which come from a visitor's own local extension.

HOW IT WORKS

The Browser Tracker is a Manifest V3 extension installed unpacked in the browser. Its manifest requests storage, alarms, idle, and tabs permissions to estimate active foreground time and keep per-domain totals locally. The portfolio dashboard stays empty until sharing is explicitly enabled in the extension and a local connection is made; it does not invent visitor statistics. The concept page's finance and PC-metric panels use fixed sample values switched by buttons and are labelled as samples.

TECHNOLOGIES

JavaScript, Manifest V3, browser storage APIs including storage.local and storage.session, the alarms, idle, and tabs APIs, and local message connections between the extension and the page. Python is listed in the portfolio for a desktop interface and a voice-to-text concept, but no Python source is present in this repository, so those are presented as concepts rather than verified builds.

INTERACTION

You can install the extension locally, switch sharing on, connect it to the dashboard, and change the sample range or metric on the concept page. There is no sign-up, hosted account, or invented live data path.

RELEVANCE

Applies to internal tools, client dashboards, and privacy-sensitive products where data should stay on a device. It also shows how to demonstrate an interface with clearly labelled sample data before a backend exists.

CURRENT STATUS

Implemented locally: the extension, the local dashboard connection, the sample concept toggles, and the extension documentation. Concept only: the Claude-assisted voice-to-text script and the Python desktop interface. No hosted service is offered.
